## 2. 구현된 기능

### CLI 및 설정 관리

- `init`: 기본 설정 생성, 기존 설정 덮어쓰기 방지.
- `config` / `config show`: JSON 설정 조회.
- `config set <키> <값>`: 설정값 검증 후 원자적 파일 교체.
- `start`: 브로커 중복 실행 확인, 독립 프로세스 생성, 준비 상태 확인.
- `status`: 로컬 브로커 실행 여부와 중앙 서버 연결 상태 조회.
- `stop`: 로컬 HTTP 종료 요청 후 잠금 해제 대기.
- `--config <FILE>`: 사용자 지정 설정 파일 경로 지원.

기본 설정은 사용자 홈의 `.devlink/config.json`에 저장합니다. 중앙 서버 주소, Agent 이름, 자동 재연결 여부, 로컬 포트, 재연결 지연, 인증 제한 시간을 설정할 수 있습니다. TypeScript의 기존 3필드 설정 형태를 읽는 호환 처리도 있습니다.

### 브로커 및 로컬 제어

- `127.0.0.1`에만 바인딩하는 HTTP 서버 구성.
- `GET /health`: 서비스·API 버전·PID·인스턴스 ID·중앙 연결 상태 반환.
- `POST /shutdown`: 정상 종료 요청 처리.
- `runtime.json`으로 포트·인스턴스·로컬 제어 토큰 공유.
- Bearer 토큰 인증 및 `Origin` 헤더가 있는 요청 거부.
- OS 파일 잠금으로 중복 실행 방지, 강제 종료 후 남은 런타임 정보 정리.
- 종료 시 중앙 연결 태스크 취소와 런타임 파일 정리.
- Windows 표준 핸들 상속을 차단하는 처리 포함.

### 중앙 서버 연결

- `DEVLINK_TOKEN` 환경 변수 기반 인증.
- `auth` 요청 및 `auth_ok` / `auth_error` 응답 처리.
- 연결 상태: `Connecting`, `Authenticating`, `Connected`, `Reconnecting`, `AuthFailed`, `Disconnected`.
- 지수 백오프 기반 재연결 및 재시도 대기 중 종료 처리.
- 인증 실패 응답 또는 종료 코드 `4001` 수신 시 재시도 중단.
- 인증 후 5초 간격 Ping, 일정 시간 응답 부재 시 재연결 처리.
- `wss` 연결에 OS 신뢰 저장소 기반 인증서 검증 사용.
- 개발용 Mock WebSocket 서버 제공.

현재 메시지 계약은 인증 및 연결 확인용 `hello` / `echo` 수준입니다. 실제 작업 요청과 결과 전달을 위한 운영 프로토콜은 후속 협의 대상입니다.

MCP 협의 상태는 **A1~A10 가확정안의 큰 방향을 유지하고, 아래 세 가지 핵심 항목의 최종 결정을 기다리는 단계**입니다. 2026-10-27 사용자 검토에서 협의 범위를 세 항목으로 정리했으며, 상대 담당자와의 최종 상호 합의나 구현 완료를 의미하지 않습니다.

| 핵심 협의 항목                 | 확정할 내용                                                              | 현재 제안 및 구현 차이                                                                                                                                                                                     |
| ------------------------------ | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 세션 활성화와 재시작 후 소유권 | 활성화 시점, Agent ID 재사용, 신규 연결·복구·교체 권한, 재시작 후 소유권 | 탐색·진단은 활성화하지 않고 등록·재개 경로에서 활성화. MVP는 먼저 복구한 세션이 빈 슬롯을 확보하되 다른 활성 세션을 교체하지 않는 방안 제안. 최신 소유자 보존 여부는 미확정이며 세션 기능은 신규 구현 필요 |
| CLI 설정 파일과 자격 수명주기  | 파일 경로·스키마·OS별 보호, 토큰 유지·교체, MCP의 파일 읽기, 제어 권한   | 일반 재시작 시 로컬 토큰 유지, 명시적 교체 시 MCP 재시작, 영속 자격과 런타임 정보 분리 제안. 현재는 시작마다 토큰 재생성, Windows ACL 설정·검증 및 MCP 권한 범위 확정 필요                                 |
| HTTP 계약과 중앙 위임 경계     | 포트, 세션·업무 API의 method·path·버전·JSON·오류·timeout, 중앙 책임      | 기본 포트 43127 사용 제안, 자동 할당 허용 범위 미확정. 세션은 브로커가 관리하고 Agent 권한·업무 상태의 최종 판단은 중앙에 위임. 요청 식별·timeout 후 결과 조회와 종료 API 권한 포함                        |

CLI가 브로커를 제어하고 Host가 stdio MCP를 제어하는 구조, 업무 자동 재전송 금지, 로컬 세션 만료와 중앙 작업 상태의 분리는 검토 기준으로 유지합니다. 교체 권한은 첫 번째 항목, MCP의 종료 권한은 두 번째·세 번째 항목, timeout 후 결과 확인은 세 번째 항목에 포함합니다. 각 표의 제안값은 최종 확정값과 구분하며, 상세 협의 기준은 [MCP 인터페이스 문서](rust/docs/mcp-interface.md)에 기록합니다.

## 4. 검증 결과

### 기존 기록: 2026-10-26

`rust/docs/verification.md`에는 Windows MSVC 환경에서 다음 검사가 통과했다고 기록되어 있습니다.

- 일반 빌드 및 릴리스 빌드.
- 통합 테스트 13개.
- 포맷 검사 및 경고를 오류로 처리한 Clippy 검사.
- 릴리스 실행 파일의 CLI 도움말 확인.

이는 **기존 문서의 기록**이며, 현재 코드와 현재 실행 환경에서 모두 통과한다는 의미는 아닙니다.

이번 작업에서는 상태 문서 작성에 집중했으며, 기능 코드나 포맷은 수정하지 않았습니다. 일반·릴리스 빌드와 Clippy는 별도로 재실행하지 않았습니다. Ubuntu, 실제 운영 중앙 서버, WSS 종단 간 연결, 실제 MCP Tool 호출의 정상 동작도 이번에 확인하지 않았습니다.

## 5. 남은 작업 및 권장 순서

1. **로컬 검증 실패 원인 확인**: 브로커 시작·준비 확인 시간 초과와 실행 환경 영향을 조사하고 통합 테스트 13개를 다시 검증합니다.
2. **포맷 정리 및 품질 검사**: `protocol.rs` 포맷을 정리한 뒤 포맷·Clippy·일반 및 릴리스 빌드를 확인합니다.
3. **CI 구성 확인 또는 추가**: Windows/Ubuntu 검사 워크플로 파일을 준비하고 실제 실행 결과를 확인합니다.
