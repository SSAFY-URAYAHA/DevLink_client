# -93 Gemini 교차검증 요청

2026-10-30 후속: 사용자가 전달한 Gemini P2 두 건을 수정했다. [후속 수정·재현 기록](story93-gemini-followup.md)을 먼저 보고, 동시 충돌의 키 원자적 반환 및 register_agent의 신원/세션 검사 우선순위를 재검토한다. 이전 검토 원본과 수정본 bundle/manifest는 별도 파일로 보존한다. 아래 9개 기준과 중앙 provider blocker의 경계는 유지한다.

사용자가 Claude 대신 Gemini로 검토하고 결과를 전달하기로 했다. 구현 커밋은 검토 및 필요한 보완 이후에만 한다. 이번 검토 대상은 **현재 미커밋 -93 변경분**이며 -94/-95/-96/-97/-52/-66 전체 구현 승인을 요청하는 것이 아니다.

Gemini에 `rust/target/story93/gemini-review-bundle.md`를 첨부하고 다음 요청을 전달한다.

> DevLink S15P31D108-93 구현을 독립적으로 코드 검토해 주세요. 설명이나 테스트 통과를 그대로 신뢰하지 말고, 첨부된 diff와 현재 소스로 수용 기준 충족 여부를 확인해 주세요. 실제 수정이 필요한 결함은 우선순위(P0/P1/P2), 파일·함수·라인, 재현 조건, 영향, 최소 수정 방향으로 정리해 주세요. 발견 사항이 없으면 없다고 명시하고, 확인하지 못한 부분은 별도로 남겨 주세요. 코드 변경이나 커밋은 하지 마세요.
>
> 확인할 사항:
> 1. register_agent는 현재 중앙 자격의 기존 Agent만 확인하며 생성·갱신·토큰 발급을 하지 않는가? 미바인딩 세션의 확인과 이후 bind가 분리되는가?
> 2. 신원·팀·Agent·세션 소유권/lease·현재 연결 검증을 위조·해제·교체·재접속 경합으로 우회할 수 없는가?
> 3. Agent Bearer의 실제 provider(`/api/v1/agent/context`, `/api/v1/agent/agents`, `/api/v1/agent/tasks`)만 사용하며 사용자용 경로/임시 actor 인자를 사용하지 않는가?
> 4. 최대 Java Long ID가 정밀도 손실 없이 문자열로 왕복하는가? prompt 원문, 상태, 전달 결과, ApiResponse와 로컬 envelope의 의미가 보존되는가?
> 5. 새 논리 요청당 requestKey를 한 번 발급해 전송 전에 내구 저장하는가? 같은 requestId의 내용 충돌·재시작·응답 유실에서 키/알려진 taskId를 잃거나 새 키로 자동 재생하지 않는가?
> 6. 자동 재전송·409 후 임의 조회·업무 FAILED 전이·중앙 권한/오프라인/ACK 정책 우회가 없는가?
> 7. 중앙 401/403과 local_auth를 혼동하지 않는가? 미확정 HTTP/code 조합·타임아웃·본문 지연·5xx·409 동시충돌을 rejected/success로 오판하지 않는가?
> 8. 요청/응답 크기, 전체 예산·본문 deadline·취소, private-file IO 대기가 heartbeat/종료를 막지 않는가? redirect/비밀 원문 노출이 없는가?
> 9. 합성 provider 회귀, 실제 Rust HTTP, 실제 중앙·DB의 증거를 구분했는가? 테스트가 구현을 따라 답만 맞추거나 중요한 실패·동시성 경로를 빠뜨리지 않았는가?
>
> 고정 중앙 02de434의 오프라인 수신자 저장 전 거부 미충족은 실제 재현한 provider 의존성 blocker다. 이를 Rust의 사전 목록 조회나 로컬 가짜 실패로 우회하라고 요구하지 말고, 해당 미충족을 성공으로 숨기는지 검토해 주세요. 중앙 -49/-84/-67/-68/-71의 구현이나 MCP 최종 DTO(-97)를 이 변경에 추가하도록 범위를 확장하지 마세요.

검토 자료는 구현 diff, 관련 현재 소스, 로컬/실제 중앙 검증 결과와 한계를 함께 담는다. 내부 테스트용 합성 자격 상수 외 실제 토큰·사용자 쿠키·비밀번호는 포함하지 않는다. 결과는 이 채팅에 전달하면 된다. **이 문서 작성 자체는 Gemini 검토 완료가 아니다.**
